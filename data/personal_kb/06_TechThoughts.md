# 技术思考

## 我对 RAG 技术的理解

### RAG 解决了什么问题

LLM 有两个核心痛点：**知识过时**（训练数据有截止日期）和**幻觉问题**（编造不存在的信息）。RAG 通过"检索 + 生成"的架构，让模型在回答问题前先去知识库查资料，有效解决了这两个问题。

### RAG 的局限性

1. **检索质量决定回答质量**：如果检索到的文档不相关，再好的模型也答不对
2. **文档切分可能割裂语义**：关键信息正好卡在两个片段之间时会被遗漏
3. **无法做深度推理**：RAG 只能"找到相关内容"，不能"综合多篇文档推导新结论"
4. **实时性有限**：知识库更新后才能检索到新内容

### 为什么选择混合检索

纯向量检索对专有名词（型号、编号）不够精确，纯关键词检索对同义词（"续航" vs "电池容量"）无法理解。混合检索结合两者优势，实际效果比单一方案好很多。

### Prompt Engineering 的重要性

同样的模型，不同的提示词，回答质量天差地别。我学到几个原则：
- **明确角色**：告诉模型"你是谁"（如：你是一个专业的客服助手）
- **设定规则**：明确什么可以做、什么不能做
- **提供示例**：Few-shot 比 Zero-shot 效果好
- **结构化要求**：让模型按特定格式输出

## 我对"AI 替代程序员"的看法

很多人担心 AI 会替代程序员。我的看法是：

1. **AI 替代的是"只会写代码的人"**，不会替代"理解业务、能设计系统的人"
2. **编程的门槛降低了**，但软件工程的复杂度没有降低
3. **未来的程序员更像"AI 的指挥者"**：不需要手写每一行代码，但要能判断 AI 写的代码对不对、好不好
4. **核心竞争力是"理解力"**：理解用户需求、理解业务逻辑、理解系统架构

## 我的技术价值观

1. **实用主义**：技术是工具，目的是解决问题。不盲目追新，选择合适的技术
2. **安全第一**：写代码时要有安全意识（XSS 防护、密码加密、权限控制）
3. **代码可读性 > 代码简洁性**：清晰比炫技重要，三个月后的自己要能看懂
4. **测试是必须的**：不写测试的代码就是"我猜它能跑"
5. **持续学习**：AI 领域变化快，保持学习的心态很重要

## 一次印象深刻的技术调试

在开发这个 RAG 系统时，遇到过一个奇怪的问题：会话列表的时间显示少了 8 小时。

排查过程：
1. 检查前端 `new Date()` 解析 → 发现后端返回的 ISO 时间字符串没有 `+00:00` 后缀
2. 检查后端 `datetime.isoformat()` → 发现 `tzinfo` 为空
3. 检查数据库存的值 → 发现 SQLite 不保存时区信息，SQLAlchemy 读出来就是 naive datetime
4. 确认根因：SQLAlchemy + SQLite 的时间处理链路中，时区信息丢失了

解决方案：
- 后端：自定义 `UTCDateTime` 类型，读取时自动补回 UTC 时区
- 前端：`parseDate()` 函数防御性处理，没有时区标记就补 `Z`

这个 bug 让我深刻理解了"时间处理在软件工程中的复杂性"。
